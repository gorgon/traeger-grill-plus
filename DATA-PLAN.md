## REQUIRED RULES — Traeger Grill Control (R1–R10, captured Nov 7, 2026 from the owner's requirements)
These rules are the app's contract. The Spec & Tests view in the app lists them with live guard status; `server/src/integrationTests.ts` enforces them. **Every future change must run the suite (`runIntegrationTests` / `runTests` action); a red suite blocks the change.**
- **R1 Real grill state rules everything** — raw states first-class (99 Offline / 3 Idle / 5 Igniting / 6 Cooking); no timer/progress while not actually cooking; timer hold while Idle/Offline. Tests T01–T03.
- **R2 Recipe drives the grill** — active stage target = grill target; drift detected → correction requested → Muse executes → confirming snapshot marks it confirmed; adaptive reading cadence near probe targets lives on Muse's monitor side. Tests T11–T12.
- **R3 Stage advancement** — completion types owner/probe/timer/grilltemp; Done ONLY on owner stages; monitored stages auto-advance on condition; manual advance on monitored stages rejected server-side; auto-advance onto an owner stage fires the alarm with the exact instruction. Tests T04–T08.
- **R4 Alarm discipline** — siren + spoken instruction until acked; acks persist server-side per session+stage+kind and survive reload/rebuild; reality cross-check auto-acks actions the snapshot proves done; app opens on the relevant screen for the cook's actual position; overlay only for NEW genuinely-due unacked owner actions. Tests T09–T10.
- **R5 Minimal modern UI** — one-row header with checked-age inside it; no Screen-awake chip, no Checking pill, no Latest card; chips only for attention items; wake lock silent, repair button only on failure. Test T22 (data contract).
- **R6 Honest refresh** — refresh is self-service first (liveRefresh pulls fresh status directly from Traeger; manual request to Muse is the fallback); tap acknowledged instantly; the checking state ALWAYS resolves — a snapshot at/after the request ends it, 90s unanswered → spinner off + honest note + fresh tap allowed; concurrent live taps join, live calls ≥15s apart. Tests T13, T32, T37 (+M1 manual-only: live MQTT round-trip).
- **R7 Tiny sparkline graphs + trend arrow** — tiny sparkline beside Grill and Probe with the expectation-coloured arrow at its end; the sparkline LINE takes the same colour as its end arrow. Drawn ONLY from real history (pushes + typed carry-forward feeder rows, never interpolated): display window 30 min, widening to 60 then the full ~2h store when the narrower window lacks ≥2 points spanning ≥3 min; nothing renders only when the whole store lacks 2 usable points. Direction uses the owner's stability band: |Δ| ≤ 3°F over the window counts as "steady" (flat arrow). Tone semantics (owner's rule: "keep it flat — green if it's almost stable; all unexpected arrows are red"): GRILL while cooking with a setpoint — steady within ±15°F of setpoint → flat green; moving TOWARD the setpoint → green; moving AWAY (rising further above, falling further below) → red; already outside ±15°F, any movement that does not close the gap → red, steady far outside the band → red. PROBE during a cook stage: rising → green; steady (stall) → flat green; falling → red. During a Rest stage: falling → green, steady → flat green, rising → red. No cook context / insufficient data → no arrow. Grill sparkline shows a faint dashed setpoint line while a cook is active. Series + `windowMinutes` exposed server-side as `trends.grill/probe`. A server feeder (artifact cron `traeger-grill-history-feeder`, every 2 min → `feedSnapshotHistory`) appends carry-forward rows during a cook; they never change `lastVerifiedAt`. Canonical tone helpers `grillTrendTone`/`probeTrendTone` in actions.ts. Tests T14–T17, T24–T26, T34, T35, T40–T46.
- **R8 Continuity** — full session recovery after restart/rebuild; server-side stage timing and holds; last picked meat restored; setpoint ranges enforced: grill 165–500°F, probe targets 100–215°F. Credentials (owner decision Nov 7, 2026, superseding the earlier no-storage posture): the Traeger login is stored ONLY in the server-side `traeger_auth` table so refresh re-authenticates unattended; the password is never returned to the page after entry, never in the client bundle/localStorage, never logged; the 24h token is cached and auto-renewed from the stored login. Muse's external checks remain as fallback. Tests T12, T18–T19, T36 (+M2 manual-only: real sign-in exchange).
- **R9 No way out mid-cook — Shutdown always confirms** — no Cancel control in the cook view; cancelCook rejected server-side while the grill is verifiably cooking; only exits are final-stage completion or Shutdown. Shutdown NEVER acts on a single tap: a confirmation dialog (⚠, current stage + probe temp, ends cook + session, grill cools, cannot be undone) must be confirmed with "Yes, shut down"; "Keep cooking"/backdrop/✕ records NOTHING — no request, no session change — until confirmation. Tests T20, T21, T23.
- **R10 Stage instructions have a lifecycle** — instruction shown BEFORE its stage as a preview on the upcoming row; delivered at the transition via alarm + YOUR TURN overlay until acked; once the stage is active and its start action is done/acked (incl. reality auto-ack) the instruction DISAPPEARS from the active card (live status only). Owner stages (the act IS the stage) keep it visible while active; it disappears when Done completes the stage. Completed stages never show it. Detail dialog keeps it for reference. Server view-model: `getDashboard.stageView[]` via `computeStageView` (state + instructionVisible + instruction). Tests T27–T30. Live check after ship: session 5 Smoke card must show no "Place roast…" text.
- Test storage: `test_runs` table (migration 0009) — suite, scenario, rule, pass/fail, detail, run timestamp, build id (`v16-spec-tests`). Suite runs on isolated TEST- sessions + synthetic snapshots; production grill_state and snapshots are saved and restored, test rows deleted; a final check verifies the production active session is untouched.

## Screen-awake fix (Nov 7, 2026 edit)
- Owner report: "app doesn't keep screen on." Diagnosis from source (render evidence clean — no console errors): the keep-awake was a single Wake Lock requested once at COOK tap / session start, with no recovery path. iOS releases a screen wake lock on Low Power Mode, low battery, or transient conditions and never restores it; the app also never re-acquired except on a visibility toggle, and outside an active cook (e.g. picker left open) no lock was even requested.
- Fix: two independent, self-healing keep-awake mechanisms, both armed whenever the app is open: (1) Wake Lock with a 15s watchdog + re-acquire on lock-release/visibility-return; (2) a 5-second silent looping MP4 (`client/src/assets/keepawake-loop.mp4`, generated locally with ffmpeg: black 160×160 + silent AAC track) played inline in a small dim corner badge — iOS does not auto-lock while media plays, and the muted+playsInline video needs no audio session (the tested voice alarm is untouched). Any tap re-arms both; the header chip now reflects reality — "☀️ Screen awake" only when a mechanism is actually live, otherwise a "Keep screen on" retry button.

## Setpoint auto-fix (Nov 7, 2026 edit)
- Owner requirement: the grill must always follow the active recipe — auto-fix setpoint mismatches instead of only warning. Note the live case that motivated it: grill setpoint 240°F vs Chuck Roast Stage 1 target 250°F.
